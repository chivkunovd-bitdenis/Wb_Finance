# Порядок применения при остановленном WB Finance

Только после проверки кода и публикации точного SHA. Этот сценарий не использует
обычный release-ozon.sh: тот требует уже здоровый работающий стек.

1. Убедиться, что API, worker, beat, image workers и auth WB Finance остановлены.
   Создать приватные холодные копии томов Redis/PostgreSQL и проверить SHA256.
2. Запустить только существующие Redis/PostgreSQL с прежними томами. Сохранить
   pg_dump. Зафиксировать Redis lists/unacked/index и intents (без payload в логах).
3. Получить опубликованную ветку, создать detached source checkout точного SHA.
   Проверить чистоту исходников. Создать образ через Dockerfile.orchestrator-recovery
   от точного старого application image: зависимости, браузер и ключи не обновляются.
4. В private override для api/worker/beat указать новый image и точные source mounts;
   data/.env сохраняют прежние пути. Worker: concurrency=1, memory=1GiB, swap=1GiB,
   max-memory-per-child=262144 (перезапуск child только после завершения задания).
   Не пересоздавать Redis с анонимным томом и не применять --remove-orphans.
5. Запустить recovery script в одноразовом ограниченном контейнере с прежним runtime
   environment и сетью WB Finance. Сначала dry-run; затем --apply --producers-stopped
   с новой приватной SQLite-копией. Скрипт сохраняет один canonical tick без ETA,
   остальные типы заданий сохраняет побайтно. Проверить отчёт и контрольные суммы.
6. Выполнить additive migration новой сборкой. Сверить сохранность intents и таблиц.
7. Поднять штатную инфраструктуру/зависимости WB Finance из прежних контейнеров.
   Поднять новый API, дождаться health, затем новый worker и beat. Прежний worker
   с дефектным кодом никогда не запускать в качестве автоматического rollback.
8. Сверить image revision + mounts с SHA; API/public health; ready/unacked/ETA,
   dispatcher и прогресс DB; память/swap/OOM и отсутствие повторных получений тиков.
   Указать длительность наблюдения; короткий старт не равен проверке часового окна.

Если проверка провалилась, остановить api/worker/beat и сохранить очереди/базу для
разбора. Не восстанавливать всю базу или Redis поверх более свежих данных автоматически.
Исходные сообщения доступны в SQLite backup, томах и pg_dump. Возврат старого кода
разрешён только при остановленных worker/beat, иначе вернётся размножение таймеров.

# Восстановление WB Finance после накопления отложенных задач

Разрешение владельца, 18.10.2026: исправить причину, удалить накопленные дубли,
сохранить другие задания и данные, поднять WB Finance и проверить очередь и сервер.
Исходный production SHA: `28a633ea074b784a3614ed24d5c6e23e00f1e700`.

## Сценарий и границы

Пользователь открывает финансы или запускает синхронизацию. Его запрос сохраняется
в базе. Для продавца выполняется один шаг за раз. Если WB просит подождать,
система сохраняет срок в базе; многочасового таймера в памяти обработчика нет.
Повторное открытие экрана, повторная доставка сообщения и перезапуск не создают
самоподдерживающиеся цепочки. Новые запросы во время работы не теряются.
Блокировка финансового API WB не останавливает доступную операцию воронки.

Никаких изменений расчётов, ключей, LLM-вызовов или соседних проектов. Не изменять
чужие локальные файлы. Сохранение в отдельной ветке, commit и push обязательны.
Выкат разрешён владельцем; merge в main не требуется для аварийного восстановления
и отдельно не выполняется. На сервере должен работать опубликованный проверенный SHA.

## Для разработки: flow trace и контракт

1. API/dashboard -> kick -> locked merge в WbOrchestratorState -> durable next due.
2. Короткий beat dispatcher -> FOR UPDATE SKIP LOCKED -> token/lease -> немедленный tick.
3. Tick -> session advisory lock на отдельном PG connection -> token/due validation
   -> один WB шаг -> locked merge прогресса -> следующий срок в БД.
4. Устаревшие и параллельные тики завершаются без вызова WB и без публикации детей.
5. Ошибка публикации, потерянный запуск и падение обработчика восстанавливаются
   диспетчером. Срок владения запуском не зависит от updated_at, который меняют kick.
6. Метаданные blocked сами по себе не являются запросом работы.

Добавляются только поля планирования, старые финансовые данные не переписываются.
Ограничения памяти/параллелизма защищают общий сервер дополнительно к устранению причины.

## Выборочная очистка

Все источники и потребители WB Finance остановлены. Сначала приватная холодная копия
томов Redis/PostgreSQL с контрольными суммами, затем инвентаризация очереди. Учитываются
ready priority lists, unacked и unacked_index. Выбирается только точное имя
`wb_orchestrator_tick`; пользователь и отсутствие цепочек проверяются по телу.
Непонятные сообщения не удаляются. Работа должна быть представлена состоянием в БД.

На пользователя сохраняется один исходный тик, его ETA снимается, чтобы обработать
состояние новым кодом. Остальные тики этого пользователя удаляются как дубли. Для
канонического unacked-сообщения разрешён перенос в исходную ready-очередь. Все другие
сообщения, включая kick, перерасчёты и Ozon, сохраняются побайтно и с прежним порядком.
Контрольные суммы intents до/после совпадают. FLUSHDB и общая purge запрещены.
Изменение возможно только если снимок очереди не изменился после проверки.

## Проверки

- 100 повторов во время паузы/со старым токеном: ноль WB-вызовов и новых сообщений.
- Конкурентные dispatch/tick/kick: одна актуальная работа, новые intents сохранены.
- Finance 429 не блокирует доступную воронку; metadata-only состояние не крутится.
- Потеря публикации/процесса: восстановление без многочасового countdown.
- Смешанная очередь: сохранность всех нецелевых ready/unacked байтов и index scores.
- PostgreSQL регрессии, целевые тесты и независимое ревью до live применения.
- После выката: SHA, health API, штатные сервисы, queue counts, отсутствие ETA/штормов,
  память/подкачка/журнал OOM. Указать фактическую длительность наблюдения и её предел.
